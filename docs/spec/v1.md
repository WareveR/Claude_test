# Family Calendar: v1 spec

Status: **accepted by David on 2026-10-02** ([Assemble the v1 spec from the resolved decisions](https://github.com/WareveR/Claude_test/issues/41)).

This spec gathers every decision on the [Wayfinder map](https://github.com/WareveR/Claude_test/issues/1) into one place, ready to be split into implementation tickets with `/to-tickets`. It follows the `/to-spec` template. The decisions themselves live in their tickets, in [`CONTEXT.md`](../../CONTEXT.md) (the glossary, whose terms this spec uses throughout) and in [`docs/adr/`](../adr/); each section links its sources so a reader can zoom in. Where assembling everything exposed a contradiction or a gap, the spec takes a default and lists it under [Assembly decisions for review](#assembly-decisions-for-review), so David can confirm or change it.

## Problem Statement

One Family plans its shared life across several heads and several phones: birthdays, holidays, school and sport activities, medical appointments, bookings, chores. Today that lives in memory, in scattered phone calendars and in chat messages. Nobody sees the whole picture, things are forgotten, nobody knows whose turn a chore is, and a wall calendar in the kitchen is always out of date. General-purpose calendar apps assume one owner per calendar, have no idea of Persons who never sign in, mix work and family, and need accounts for children.

## Solution

A private, installable web app for exactly one Family (ADR-0001), signed in with one shared Family Password (ADR-0003), running at €0 a month on Cloudflare (ADR-0004).

The Family puts Entries on the calendar (Timed or All-day, possibly repeating, each with an Entry Type and the Persons it is for), keeps Tasks and seasonal Checklists, and sees everything in day, week, month and year views plus a Tasks view, narrowed by a Person Filter. The views carry a 15-day weather forecast for the selected Weather Location and the Public Holidays of the Family's country, region and municipality. Every morning an AI-written Briefing at the top of the day view says what is coming up. Entries and Tasks can be created and changed by speaking or typing one sentence (Voice Entry). Phones get Reminders as push notifications; other calendar apps can subscribe to a read-only Calendar Feed. A tablet on the wall runs in Display Mode. Private Entries and Tasks stay discreet on the wall, on lock screens and in the Feed. Errors are shown at once with a code and can be reported; the data is backed up every night and can be exported at any time.

The UI ships in pt-PT and English.

## User Stories

## Implementation Decisions

### Platform and architecture

Fixed by ADR-0004 and ADR-0005 (sources: [#14](https://github.com/WareveR/Claude_test/issues/14), [#15](https://github.com/WareveR/Claude_test/issues/15)):

- **One Cloudflare Worker** serves the React single-page app (TypeScript, Vite, React Router, Tailwind) and a small **Hono** JSON API. The browser renders everything; the Worker answers API calls, so each request stays inside the Workers Free 10 ms CPU limit.
- **Bindings**: D1 (created with the `eu` jurisdiction) through Drizzle ORM with numbered migrations; R2 for images and a separate R2 bucket for Backups; Workers AI; Cloudflare Email Service; one Cron Trigger schedule.
- **Client data**: TanStack Query, refreshing every minute and on focus, with its cache persisted on the device for offline reading; vite-plugin-pwa for install and updates.
- **Dates**: date-fns plus its time-zone add-on for maths, the browser's Intl for formatting; no Temporal.
- **Translations**: i18next, one JSON file per language (pt-PT, en), shared by the UI and the Worker's emails.
- **Calendar views**: our own components, no calendar library.
- **Budget**: €0 a month plus an own domain (~€10 a year, needed to send email). Workers Paid ($5 a month) is the accepted fallback if a free limit is hit.

### Modules

The code is organised around a few deep modules, each with a small interface:

- **Calendar core** (pure TypeScript, shared by browser and Worker, no I/O): wall-clock date/time values in the Family Time Zone; Timed and All-day ranges with inclusive ends; Repetition expansion into Occurrences for a date window, applying the exceptions (skips and overrides) and the last-day-of-month rule; "this and the following" splitting; Task overdue state and the next due date of a repeating Task; Checklist period, progress and next round; Person Filter matching (any-of, Family-wide switch); Reminder fire times; Public Holiday calculation through `date-holidays`; Birthday age. This is where most logic and most unit tests live.
- **API** (Hono on the Worker): sign-in and setup, Signed-in Devices, Family settings, Persons, Entry Types, Entries and Occurrence exceptions, Tasks, Checklists, Weather Locations and forecast, Briefing, Voice Entry, Calendar Feed, push subscription, Error Log, Export, images. It returns stored rules plus exceptions; the browser expands Occurrences with the calendar core for the visible window.
- **Scheduler** (the Worker's `scheduled` handler): one Cron Trigger every 5 minutes that dispatches by clock time to Reminders (every run), weather refresh (hourly), Briefings (daily before dawn, plus pending rewrites), the nightly Backup, the daily error summary email, and image cleanup (daily). One schedule keeps within the free plan's Cron Trigger allowance.
- **AI adapter**: one place that calls Workers AI for the Briefing and for Voice Entry, builds the prompts, validates the model's JSON output against a schema, and returns a typed result or a "failed" signal that triggers the fallback (countdown list or plain form).
- **Views** (React): header, day, week, month, year, Tasks view, Display Mode board, Entry/Task/Checklist forms, Settings, Voice Entry sheet.

### Data model

Source: [What does the stored data look like?](https://github.com/WareveR/Claude_test/issues/37).

- **Tables** (roughly): `family` (settings), `signed_in_device`, `person`, `person_nickname`, `entry_type`, `entry`, `entry_person`, `entry_reminder`, `occurrence_exception`, `task`, `task_person`, `checklist`, `checklist_person`, `checklist_round`, `reminder_sent`, `calendar_feed` (+ its Persons), `weather_location`, `weather_cache`, `briefing`, `error_log`.
- **Ids**: random text ids on every record; they double as the stable UID in the Calendar Feed.
- **Times**: a Timed Entry stores a wall-clock start (date + time) and optional wall-clock end, no UTC conversion (ADR-0002). An All-day Entry stores a start date and an inclusive end date. A Task stores a due date and optional due time the same way. Only technical timestamps (created, changed, Reminder sent, Briefing written, last used, error time) are UTC instants.
- **Repetition**: plain fields on the Entry (frequency, interval, weekdays, end: never / until date / count). RRULE text is generated only for the Calendar Feed. `occurrence_exception` is keyed by Entry and the Occurrence's original date and holds a skip or the overridden fields. "This and the following" ends the old Entry the day before and creates a new Entry from that Occurrence on, both linked by a series id; exceptions after the split move to the new Entry.
- **Repeating Tasks**: ticking one keeps it as done and creates a new Task with the next due date, linked by a series id.
- **Checklists**: `checklist_round` stores only each closed round's result ("2025: 7 of 8"). A new round resets its Tasks' done state and shifts their stored dates with the period.
- **Birthdays**: the synced Birthday Entry points at its Person; that link fixes its date and Person.
- **Deleting**: hard delete for Entries, Tasks and Checklists; no Trash. Persons are archived while anything mentions them.
- **History**: only created and changed times; no change log, no "changed by".
- **Settings split**: browser only: Person Filter, Display Mode, spoken readback, hiding Public Holidays. Server, on the Signed-in Device: name, last used, session hash, push subscription, language, Reminder settings (Persons or off). Server, Family-wide: name, Family Time Zone, Family Language, holiday countries/regions/municipality, selected Weather Location, recovery email, last full Export time.
- **Images**: only Person photos and Entry Type thumbnails are uploaded. The browser shrinks them to about 256 px; they are stored in R2 under new random keys, never overwritten, served by the Worker only to Signed-in Devices. An unreferenced image is deleted 30 days after it was last used ([#39](https://github.com/WareveR/Claude_test/issues/39); this replaces #37's "replacing deletes the old one"). An Entry's own icon comes from the app's fixed icon set.
- **Briefings**: only the latest per Family or Person and per language, with the time written.
- **Weather**: the last Open-Meteo forecast per selected Weather Location, kept up to a day.
- **Migrations**: numbered Drizzle migrations, additive only (see Build and deploy).

### Sign-in, devices and security

Sources: [#13](https://github.com/WareveR/Claude_test/issues/13), [#38](https://github.com/WareveR/Claude_test/issues/38), ADR-0003.

- **Setup**: the setup code is a Worker secret. The first-run screen asks for it, then the Family's name, Family Password, recovery email, Family Language and Family Time Zone (pre-filled from the browser). The screen locks once the Family exists. Setting a different setup code later reopens a screen that only chooses a new Family Password (the Worker keeps a hash of the last code used to notice the change).
- **Password hashing**: PBKDF2-SHA-256 through WebCrypto with a random 16-byte salt and **100,000 iterations**, the highest count the Workers runtime accepts. The stored hash records algorithm and iterations so it can be raised later. Sign-in is rare (a device signs in about once a year), so its CPU cost is acceptable on Workers Free. See [Assembly decisions](#assembly-decisions-for-review).
- **Throttling**: after 5 wrong attempts, each further attempt waits progressively longer, counted per client IP and also globally for the Family.
- **Sessions**: a random token in a cookie that is `HttpOnly`, `Secure`, `SameSite=Lax`, host-only with the `__Host-` prefix; stored only as a hash on the Signed-in Device; valid a year from last use. Changing the password or recovering it deletes every Signed-in Device.
- **Device name**: taken from the browser and platform ("Chrome on Android"), editable on the Signed-in devices page.
- **Recovery**: a single-use link valid 1 hour, emailed to the recovery address through Cloudflare Email Service; the screen gives the same answer whatever address is typed. A new recovery email works only after Cloudflare's verification message is confirmed. Password and recovery-email changes send a notice email.
- **Requests**: state-changing requests are accepted only when their `Origin` is the app's own. Responses carry a strict CSP (`self` only), HSTS, `frame-ancestors 'none'` and `Referrer-Policy: no-referrer`.
- **Revoked device**: when the API rejects the session, or the device signs out, the browser deletes the persisted query cache and cached API responses at once.
- **Workers AI**: acceptable; may run outside the EU (inferred, not verified). The Briefing never sends notes or Private items; Voice Entry sends the sentence and the candidate Entries and Tasks it needs.
- **GDPR**: household exemption (Art. 2(2)(c)); no privacy notice or DPA. Data in the EU.

### Persons and Entry Types

Sources: [#3](https://github.com/WareveR/Claude_test/issues/3), [#10](https://github.com/WareveR/Claude_test/issues/10), [#11](https://github.com/WareveR/Claude_test/issues/11), [#43](https://github.com/WareveR/Claude_test/issues/43).

- A Person has a name, colour, optional photo, optional Nicknames, optional date of birth, and an archived flag.
- Built-in Entry Types and their defaults:

  | Entry Type | Defaults | Default Reminders |
  |---|---|---|
  | Birthday | yearly, all-day, shows age | 3 days before, on the day |
  | Holiday | all-day, several days | none |
  | Appointment | timed, location | 1 day before, 1 hour before |
  | Booking | timed, location | none |
  | Activity | timed, weekly Repetition | none |
  | Event | timed, location | none |
  | General | none (the catch-all) | none |

  Reminders for types other than Birthday and Appointment were not discussed; "none" is the assembly default.
- An Entry Type's defaults cover time of day or all-day, Repetition, Importance, location, Persons, notes and Reminders; none restricts an Entry.
- Built-in type names come from the translation files until the Family renames them.

### Entries, Repetition and Birthdays

Sources: [#4](https://github.com/WareveR/Claude_test/issues/4), [#12](https://github.com/WareveR/Claude_test/issues/12), [#11](https://github.com/WareveR/Claude_test/issues/11).

- Entry fields: title, Entry Type, time shape (Timed with optional end, or All-day range), Persons, Importance (default Normal), location (free text), notes, icon (from the fixed set; overrides the type's), Reminders (offsets), Private, Repetition.
- An Occurrence override may change any field except the Repetition itself.
- A synced Birthday Entry is created, moved and removed only through its Person's date of birth; it can't be deleted directly. Archiving its Person asks whether to keep it; if kept, it loses its Person link and becomes Family-wide (and an ordinary, hand-editable Birthday Entry).

### Tasks and Checklists

Sources: [#26](https://github.com/WareveR/Claude_test/issues/26), [#44](https://github.com/WareveR/Claude_test/issues/44).

- Task fields: title, notes, due date, due time, Persons, Private, done (with when), Repetition (not for Tasks in a Checklist), Checklist (at most one).
- **Next due date of a repeating Task**: the first date of its Repetition after today, so ticking an overdue weekly Task never produces another overdue one. This is an assembly default.
- **Editing a repeating Task** changes it and the ones that follow, since only one undone Task exists at a time.
- Checklist fields: name, optional period (start, end), Persons (defaults), Repetition or none, Reminder at the start (on by default), and its Tasks. "Use again" starts a new round by hand.
- A Checklist has no Private switch; its Tasks can each be Private. Assembly default.

### Views

Sources: [#16](https://github.com/WareveR/Claude_test/issues/16) (variant B), [#26](https://github.com/WareveR/Claude_test/issues/26), [#28](https://github.com/WareveR/Claude_test/issues/28), [#8](https://github.com/WareveR/Claude_test/issues/8), [#42](https://github.com/WareveR/Claude_test/issues/42), [#44](https://github.com/WareveR/Claude_test/issues/44).

- **Addresses**: each view has its own address with the date (for example `/day/2026-10-08`, `/week/2026-10-05`, `/month/2026-10`, `/year/2026`, `/tasks`); `/` opens today's day view.
- **Header** (every view): current time, weekday, day and month, today's weather icon and high/low for the selected Weather Location.
- **Day**: hourly weather strip (today only; another day shows a small weather badge next to its title), Briefing band (today only), Tasks accordion, then a time grid with an all-day row on top.
- **Week**: Tasks accordion, then a seven-column time grid with an all-day row; the week starts on the language's first day (Monday for both v1 languages).
- **Month**: a month grid; tapping a day lists that day's Entries and its Tasks accordion below.
- **Year**: one row per month in a fixed 37-column grid that always runs Saturday to Sunday (the one exception to the language's first day). High-importance days are filled with the Entry Type's colour, other Entries show a dot, Checklist periods show as a bar, and tapping a day opens its month. No weather.
- **Entries in grids**: filled with the Entry Type colour and icon, Persons as initials avatars in their colours. Multi-day Timed Entries span the grid columns; multi-day All-day Entries span the all-day row. A Timed Entry without an end takes a small slot at its start.
- **Importance in the views** (assembly default; only the year view was decided in #16): High is drawn bolder (a stronger fill and a High marker) in day, week and month; Low is drawn lighter; the year view fills only High days.
- **Tasks accordion**: one collapsible line ("Tasks 7 · 2 overdue") holding the period's dated Tasks and, when the period includes today, every overdue Task. Tasks are ticked there; done ones are struck through. Dated Tasks are not drawn inside the time grid.
- **Checklists**: the period is an all-day bar ("Summer cleaning 3/8") in week, month and year; its dated Tasks join that day's accordion.
- **Shading**: Saturdays and Sundays shaded in every view; Public Holidays shaded in their own colour, which wins, with the holiday name in the all-day row (week, day) or as a small label (month).
- **Weather**: icon (sunny, partly cloudy, cloudy, rain, showers, thunder, snow, fog) with high/low °C on each of the next 15 days in day, week and month; days 8–15 lighter; none on past days or the year view. Tapping any weather opens a confirmation, then IPMA (Portugal) or yr.no (elsewhere) in a new tab.
- **Tasks view**: Overdue, Today, Upcoming (by due date), No date (newest first); "Show done" lists done Tasks, most recent first. A Checklist is one expandable row with progress in the group of its end (or No date); its dated Tasks also show alone, labelled with its name; undated ones only inside it.
- **Person Filter panel**: Persons (several), Family-wide switch, Public Holidays switch. It applies to Entries, Tasks (a Task with no Persons counts as Family-wide), Checklists (shown when any Task matches) and the Briefing choice.
- **Theme**: light and dark, following the device setting. Line icons, no emoji.

### Display Mode

Source: [#35](https://github.com/WareveR/Claude_test/issues/35) (variant A + week navigation + Person Filter), [#5](https://github.com/WareveR/Claude_test/issues/5), [#40](https://github.com/WareveR/Claude_test/issues/40).

- Landscape board under the fixed header. Left column, always today: Briefing band, hourly weather strip, Tasks accordion (open), today's Entries as a large list with past ones dimmed. Right: a seven-column time grid with an all-day row, starting today (rolling seven days).
- ‹ › move the grid a week; a pill shows another week is displayed and returns on tap; after 3 minutes untouched the board returns to today. The left column never moves.
- Filter button beside the week navigation with the selected Persons' avatars; applies to the whole board; remembered on the tablet; not reset by the return to today.
- Allowed: ticking Tasks, read-only Entry details, the Person Filter, the weather confirmation. No editing, no Voice Entry, no Error Log, no Export.
- Private Entries and Tasks show only "Private" and their time.
- Screen Wake Lock keeps the screen awake; larger text; rolls over at midnight; reloads overnight when a new version is waiting. Entered from the "Wall" tab of the view switcher on any device; a visible "Leave wall view" button in the header exits.

### Weather

Source: [#28](https://github.com/WareveR/Claude_test/issues/28).

- Weather Locations are found with Open-Meteo's geocoding search; up to 10 saved; one selected Family-wide; with none saved, no weather shows anywhere.
- The Scheduler fetches the Open-Meteo forecast (16 days daily + today hourly with chance of rain) for the selected location at most hourly, and at once when the selection changes. The API serves the cache; after failures the last forecast is served for up to a day, then nothing.
- Offline devices show their last forecast. The forecast-site link uses IPMA for locations in Portugal and yr.no otherwise.

### Public Holidays

Source: [#8](https://github.com/WareveR/Claude_test/issues/8).

- Calculated in the browser (and on the Worker for the Briefing) by `date-holidays` from the Family's countries, optional regions and municipality; Portugal national by default. No network, works offline.
- Names in the device's language. Not Entries: no editing, no Reminders, not in the Calendar Feed or Export. A municipality `date-holidays` doesn't cover is entered as a yearly Entry by hand.

### Briefing

Source: [#42](https://github.com/WareveR/Claude_test/issues/42), [#38](https://github.com/WareveR/Claude_test/issues/38).

- Candidates: the next ~60 days of Entries (Occurrences expanded), Tasks (overdue, today, upcoming), Checklists (progress, end), Birthdays and Public Holidays, as titles, dates, Persons' names and Importance. Never notes, never Private Entries or Tasks.
- Workers AI picks 3 to 5, favouring High Importance and closeness, writes a few sentences in the requested language, and may add a suggestion or question (plain text). The output marks which phrases come from which Entry or Task so the view can link them.
- One Briefing for the Family and one per non-archived Person, for each language in use by a Signed-in Device.
- Written daily before dawn (05:00 Family Time Zone) by the Scheduler; marked for rewrite when an Entry or Task in the next 7 days changes and rewritten on the next Scheduler run (so a burst of edits causes one rewrite); rewritten at once by Refresh. Never written on page load.
- Fallback: a plain list of the same candidates with a countdown and date.
- Collapsible band; collapsed state remembered per device.

### Voice Entry

Sources: [#27](https://github.com/WareveR/Claude_test/issues/27), [#43](https://github.com/WareveR/Claude_test/issues/43).

- One microphone button. Chrome, Edge and Safari use the browser's speech recognition in the device's language; a text field to type is always available, and on Firefox it is the only input (with the keyboard's dictation).
- The Worker sends Workers AI the sentence, today's date, the Family Time Zone, Persons with Nicknames, Entry Types, and (for changes) the candidate Entries and Tasks from 7 days ago to 90 days ahead plus undated and overdue Tasks. The model returns either a new Entry/Task or a change to one target, validated against a schema.
- Outcomes: one target, proceed; several, ask and show up to 3 to pick by voice or tap; none, "Not found", nothing changes; two targets in one sentence, "one at a time". Deletion is refused. A synced Birthday Entry's date and Person can't change.
- Repeating Entries: unless the sentence says ("always", "from now on"), ask "only this time or from now on?"; a change to the Repetition itself applies from now on (this and the following).
- Readback through speech synthesis plus on screen; "yes"/"sim"/"guarda" saves and shows "Saved · Undo" for about 10 seconds; "no", silence or an unclear answer opens the filled-in form. Save and Edit buttons always work. Readback off: the form always opens.
- Model failure or exhausted allowance: the plain form opens with the sentence as the title.
- Voice Entry doesn't create Checklists or add Tasks to them in v1, and is hidden in Display Mode.

### Reminders

Source: [#7](https://github.com/WareveR/Claude_test/issues/7), [#38](https://github.com/WareveR/Claude_test/issues/38), [#44](https://github.com/WareveR/Claude_test/issues/44).

- Web Push with VAPID (private key a Worker secret). On iPhone it needs the app installed to the home screen; the app asks for notification permission from Settings, not on first open.
- Every 5 minutes the Scheduler finds Reminders due since its last run (Entries' offsets per Occurrence, Tasks' due times, Checklists' starts), sends each to the devices whose Reminder Persons match (a Family-wide item goes to every device with Reminders on), and records it in `reminder_sent` so it is never sent twice. Expired push subscriptions are removed.
- Text: title and time ("Dentist, 10:00"); never notes; Private: "Reminder at 10:00". In the device's language. Tapping opens the Entry or Task.
- A dated Task always has exactly one Reminder (due time, or 09:00 on its due day); it has no per-Task Reminder settings. Assembly default.

### Calendar Feed

Source: [#7](https://github.com/WareveR/Claude_test/issues/7), [#38](https://github.com/WareveR/Claude_test/issues/38).

- A Feed has a name, chosen Persons, a Family-wide switch (on by default, as in the Person Filter) and a secret stored as a hash. Because only the hash is kept, the full URL is shown once when the Feed is created or replaced. Assembly defaults.
- The .ics contains Entries only (no Tasks, Checklists or Public Holidays), with RRULE and EXDATE/RECURRENCE-ID for exceptions, record ids as UIDs, and Private Entries as "Busy" with no notes or location.

### Errors and Error Log

Source: [#40](https://github.com/WareveR/Claude_test/issues/40).

- Every failure shows a dismissible notice in the device's language: what failed, what to try, a short code (ERR-7F3K). "See details" shows action, time, app version, technical message.
- `error_log` stores time, code, device, app version, screen/action, technical message and report comment; never notes or titles of Private items. Kept 90 days. Readable in Settings › Error log on every Signed-in Device except in Display Mode.
- Report adds an optional comment and emails the recovery address at once (a few per hour at most). The Scheduler sends a daily summary email on days with errors. Errors that happen offline are queued on the device and sent when it is back online.
- No external error service; Workers Logs remain for deeper digging.

### Backup, Export and restore

Source: [#39](https://github.com/WareveR/Claude_test/issues/39).

- D1 Time Travel (7 days on the free plan) plus a nightly full JSON Backup by the Scheduler to a separate R2 bucket; keep 30 nightly and the first of each month for 12 months. A failed Backup goes to the Error Log and the daily summary.
- Full Export (ZIP with the JSON and all images) and .ics Export (all Entries) from Settings, on any Signed-in Device except Display Mode. Both include Private items, archived Persons, closed Checklist rounds and Family settings; never the password hash, secrets, Signed-in Devices or the Error Log. The browser assembles the ZIP from API responses, which keeps the Worker within its CPU limit. Settings shows when the last full Export was downloaded.
- No import. A restore replaces the whole database by hand, following a runbook in the repo (Time Travel within 7 days, else a nightly Backup or a full Export).

### Languages, offline and refresh

Sources: [#5](https://github.com/WareveR/Claude_test/issues/5), [#6](https://github.com/WareveR/Claude_test/issues/6).

- pt-PT and English; a new device starts in its browser's language when supported, otherwise the Family Language; the device's choice is stored on its Signed-in Device record. Both v1 languages use dd/mm/yyyy, Monday first, 24-hour.
- Installable PWA; the last loaded data and the app shell are readable offline; edits need a connection and are disabled offline with a notice.
- Refresh every minute and on focus; no live connection.
- Supported browsers: the last two major versions of Safari (iPhone, iPad, Mac), Chrome, Edge and Firefox.

### Build, test and deploy

Source: [#40](https://github.com/WareveR/Claude_test/issues/40).

- GitHub Actions on every PR: typecheck, ESLint, Prettier check, tests, build; all must pass to merge to `main`.
- On merge to `main`: record a D1 Time Travel bookmark, apply the numbered Drizzle migrations to the remote D1, then deploy with Wrangler. Migrations are additive only; a drop waits for a later release. Rollback = restore to the bookmark and redeploy the previous version.
- Environments: local (Wrangler with local D1/R2, `.dev.vars` git-ignored) and production. No staging, no per-PR previews.
- Secrets: setup code, VAPID private key and email settings as Worker secrets; GitHub holds only the Cloudflare API token and account id. Workers AI, D1, R2 and Email are bindings.
- The installed PWA updates itself on the next open; a Display Mode tablet reloads overnight when a new version is waiting.

## Testing Decisions

Source: [#40](https://github.com/WareveR/Claude_test/issues/40).

- **Good tests** check behaviour through a module's public interface (dates in, Occurrences out; HTTP request in, response and stored state out), never internal helpers or Drizzle queries. They read as examples of the glossary ("a monthly Entry on the 31st falls on 30 April").
- **Seams**, highest first:
  1. **The API on the real Worker against a local D1** (Vitest Workers pool). The main seam: sign-in, CRUD, Repetition exceptions and splits, Tasks and Checklists, Person Filter queries, Calendar Feed output, Export content, Scheduler jobs (called directly with a fixed clock), with Workers AI, Open-Meteo, Email and Push replaced by fakes at the binding.
  2. **The calendar core** (Vitest unit tests): Repetition expansion, last-day-of-month, inclusive ranges, summer-time changes in the Family Time Zone, overdue, next repeating Task, Checklist rounds, Reminder fire times, Public Holidays, ages.
  3. **End-to-end** (Playwright, a handful): sign in, create an Entry, view a week, tick a Task.
- **Required before v1**: the core unit tests and the API integration tests. The UI is otherwise tested by hand against the reference designs.
- **Prior art**: none yet; the repo has no code. The first implementation ticket sets up the Vitest Workers pool and one example test of each kind.

## Out of Scope

From the map's Out of scope, plus what assembly ruled out:

- Two-way sync with Google, Apple or Outlook calendars; importing .ics files or previous Exports.
- Native mobile apps.
- Individual sign-ins per Person, roles and view-only devices; passkeys and Google/Apple sign-in.
- Several Families per installation (ADR-0001).
- Commercial or business use.
- Full calendar-style repeat rules ("last Friday of the month").
- Self-hosting on a home server.
- Offline editing and live (instant) sync.
- Per-device date/time format settings; per-Entry time zones.
- Per-device or per-Entry Weather Locations.
- Email reminders.
- Deleting by voice, a back-and-forth voice chat with context, and Checklists by voice.
- Trash, change history, single-item restore and an in-app restore.
- Search across Entries and Tasks (never discussed on the map; see Assembly decisions).
- Staging environments, per-PR previews and external error services.

## Further Notes

### Assembly decisions for review

Putting everything together exposed these gaps and small conflicts. Each has a default in the spec above; David accepted all eleven on 2026-10-02.

1. **Password hash** (#38 left it to the spec): PBKDF2-SHA-256, 100,000 iterations, the Workers runtime's maximum. Stronger hashes (Argon2, scrypt) don't fit 10 ms of CPU.
2. **Next due date of a repeating Task** (#26 open): the first Repetition date after today, so an overdue weekly chore ticked late doesn't come back already overdue.
3. **Task Reminders** (#7 gave timing, not settings): one fixed Reminder per dated Task, no per-Task offsets or switch.
4. **Importance in day, week and month** (#16 only decided the year view): High bolder, Low lighter.
5. **Calendar Feed and Family-wide Entries** (#7 open): included by default, with a switch per Feed. Because the secret is hashed (#38), the Feed URL is shown only once, at creation or replacement.
6. **Default Reminders for the other Entry Types**: none, except Birthday and Appointment as decided in #7.
7. **Private Checklists**: no switch on the Checklist itself; its Tasks can be Private.
8. **Family Time Zone at setup**: asked on the setup screen, pre-filled from the browser (ADR-0002 assumes it exists but no ticket said where it's set).
9. **Briefing in Display Mode**: #35's layout predates #42; the Briefing band goes at the top of today's column.
10. **Images**: #39 ("never overwritten, deleted 30 days after last use") replaces #37's "replacing an image deletes the old one".
11. **Search**: never discussed; left out of v1.

### Risks to recheck at build time

- **Workers AI allowance** (10,000 neurons a day): the Briefing writes (1 + Persons) × languages each morning plus rewrites, and Voice Entry sends candidate lists. Estimated to fit for one Family, not measured. If it doesn't, rewrites fall back to the countdown list first.
- **Workers Free CPU (10 ms)**: password hashing, the nightly Backup's JSON of the whole database, and Briefing candidate expansion are the heaviest jobs. The Backup can be written table by table across Scheduler runs if needed; otherwise the $5 Workers Paid fallback applies (ADR-0004).
- **PBKDF2 iteration cap**: the 100,000 limit is from Workers' WebCrypto behaviour as remembered at assembly time; confirm it.
- **`date-holidays` municipal coverage** for Portugal is unverified (#8).
- **Workers AI data location**: may run outside the EU; inferred from Cloudflare's docs (#38).
- **Domain**: `phinestsolutions.com` availability on Cloudflare Registrar is still to check (#14).
- **iPhone push** works only for the app installed to the home screen (#7).

### Glossary consistency

Every term above is used as defined in `CONTEXT.md`. The **Person Filter** entry was sharpened alongside this spec: Tasks with no Persons count as Family-wide, and the panel also holds the Public Holidays switch.
